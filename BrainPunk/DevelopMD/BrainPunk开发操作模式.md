# BrainPunk 开发操作模式

创建时间：2026-06-15  
归纳范围：2026-06-08 至 2026-06-14 的 BrainPunk 开发节奏、知识库工作流、Spec Kit 产物和项目内约束。  
用途：作为后续功能开发、关卡修改、风险评估和 AI 协作的操作入口。

## 1. 核心结论

上周形成的有效模式可以概括为：

> 先把需求变成可验证的规格，再按最小范围实现；每个功能都要留下规格、任务、实现、验证证据、功能记录和风险记录；编辑器内表现、资源绑定、真机验收由开发者确认，AI 负责代码、文档、静态分析、风险扩散和操作清单。

这套模式适合 BrainPunk 当前状态：关卡数量多、已验收内容多、Unity Prefab/资源绑定多、移动端横屏体验和已发布关卡稳定性优先级高。

## 3. 你的操作模式

### 3.1 你的职责

- 定义玩家可感知目标：最终看到什么、点什么、失败/通关怎么判定。
- 确认表现节奏：动画、等待、显隐、点击区域、触控手感、移动端横屏体验。
- 操作 Unity Editor：Prefab 引用绑定、资源拖拽、Inspector 参数、场景/Prefab 保存。
- 执行运行验收：Unity PlayMode、Android/iOS 横屏冒烟、截图/日志反馈。
- 决定提交与合并：用户验收前不默认 commit/push。

### 3.2 AI 的职责

- 读取规则、规格、既有文档和相关代码，先确认边界再动手。
- 将需求拆成 `spec / plan / tasks / quickstart / risk` 等可执行产物。
- 编写或修改代码，保持改动局部、可回滚、符合既有系统。
- 输出 Unity Editor 操作清单，明确哪些引用、参数、资源需要开发者在编辑器内处理。
- 做静态验证、编译验证、风险扩散分析，并把未验证项明确记录。
- 同步更新 `DevelopMD/已有功能设计与使用记录/YYYY-MM-DD.md` 当天记录和关卡局部文档，原历史记录保持只读。

### 3.3 默认分工边界

| 工作项 | 默认负责人 | 说明 |
|---|---|---|
| 代码实现 | AI | 保持局部、小步、可回滚 |
| 规格/计划/任务文档 | AI | 需要能直接驱动实现和验收 |
| 功能说明/风险评估 | AI | 关卡级改动必须写在关卡目录 |
| Prefab 引用绑定 | 开发者 | AI 输出字段和目标对象清单 |
| Inspector 参数调节 | 开发者 | AI 给建议值和影响说明 |
| PlayMode/真机验收 | 开发者 | AI 给最短验证路径 |
| commit/push | 开发者 | 除非明确授权 |

## 4. 标准开发工作流

### Step 1：会话启动

每次开始任务时先确认三类状态：

- 当前工作区：`git status --short`
- 当前功能入口：`.specify/feature.json` 或 `../.specify/feature.json`
- 当前约束：`AGENTS.md`、项目宪法、相关 `DevelopMD` 和邻近模块文档

如果发现工作区已有未提交改动，默认视为用户已有工作，不回滚、不覆盖，只在必要时读懂并绕开。

### Step 2：需求定界

把需求先写成四句话：

- 玩家目标：玩家最终要感知到什么变化。
- 影响范围：涉及哪个关卡、UI、Prefab、配置、脚本。
- 不做范围：哪些共享系统、旧关卡、存档、打点、资源管线不碰。
- 验收标准：PlayMode 或真机上怎么证明完成。

需求不清楚时，优先问关键问题；能从本地文档和代码确认的，不反复询问。

### Step 3：规格化

中大型功能使用 Spec Kit 节奏：

1. `spec.md`：用户故事、范围、验收标准。
2. `plan.md`：技术上下文、宪法检查、原始行为基线、风险与回滚。
3. `research.md`：关键决策和既有系统证据。
4. `data-model.md`：状态、对象、事件、生命周期。
5. `contracts/`：脚本接口、Prefab 约定或调用约定。
6. `quickstart.md`：开发者可执行的验证清单。
7. `tasks.md`：按依赖和用户故事拆分的任务列表。

小修复可以压缩为轻量方案，但仍要保留：目标、范围、不做范围、验证方式、风险与回滚。

### Step 4：实现前证据读取

实现前至少完成：

- 搜索 `DevelopMD/` 是否已有模块说明。
- 搜索目标类、Prefab、事件、资源名。
- 读取邻近功能说明和风险评估。
- 对关卡改动，确认原始行为基线、失败/重开/退出/通关路径。
- 对 Editor 生命周期相关任务，先读 `DevelopMD/Editor态开发约束.md`。

所有结论必须区分：

- `事实`：有本地代码、Prefab、文档或日志证据。
- `直接结论`：由事实直接推出。
- `假设`：需要 PlayMode、设备或策划确认。
- `缺失证据`：当前没有覆盖的地方。

### Step 5：局部实现

实现时遵循以下规则：

- 关卡需求优先放在对应 `Level_*` 局部脚本、Prefab 和文档里。
- UI 辅助优先靠近使用方，不提前抽共享框架。
- 不为了复用改动已验收关卡的行为。
- 不在编辑器态入口触发运行时数据链、DB、Save、Manager 初始化或 Instantiate。
- 不隐藏行为变更：如果会改玩家可见行为，必须重新进入规格和验收流程。
- 对事件订阅、DOTween、协程、延迟回调，必须有禁用/销毁/重开清理路径。

### Step 6：开发者操作清单

涉及 Unity Editor 的任务，AI 输出清单，开发者执行：

- 打开哪个 Prefab 或 Scene。
- 给哪个 GameObject 挂哪个脚本。
- 哪些字段绑定到哪些对象。
- 哪些参数建议值是多少。
- 保存方式：Apply Overrides / Save Scene / Save Project。
- 验证入口：从哪个关卡、哪个面板、哪个按钮开始测。

### Step 7：验证与证据

至少记录四类结果：

- 静态检查：是否引入 `DB`、`Save`、`RemoteConfig`、`Instance`、`Instantiate`、`OnValidate`、`ExecuteAlways` 等风险入口。
- 编译结果：`dotnet build Assembly-CSharp.csproj --no-restore` 或说明无法执行原因。
- PlayMode 验证：进入、交互、失败、重开、退出、通关、关闭重开。
- 移动端验证：Android/iOS 横屏触控、布局、性能、平台差异；未做则明确写为未验证。

不能把“看起来没问题”当作证据。未验证项要写入文档，不要在结论中当作已完成。

### Step 8：文档同步

功能完成或有实质发现后，同步更新：

- `DevelopMD/已有功能设计与使用记录/YYYY-MM-DD.md`（同日更新同一个文件）
- 关卡目录下的 `功能说明.md`
- 关卡目录下的 `风险评估.md`
- 对应 `specs/*/tasks.md` 的任务状态
- 必要时更新 `quickstart.md` 或验证清单

关卡风险评估至少包含：

- 原始行为基线
- 受影响文件/资源
- 使用的既有系统
- 风险项
- 验证证据
- 未验证缺口
- 回滚路径
- 待确认事项

### Step 9：每日风险评估

每日或阶段性收尾时，按 Git 变更驱动风险工作流执行：

1. 扫最近三天 commit。
2. 扫当前工作区未提交变更。
3. 从直接修改文件出发，扩散到调用链、回调链、资源链、状态链、数据链、打点链。
4. 按 P0/P1/OBS 输出风险。
5. 生成风险报告和功能基线。

禁止只按“广告、弹窗、主流程、打点”等固定模块泛泛复述旧风险；必须能回答风险来自哪个 Git 变更入口、如何扩散到运行时、为什么是这个优先级。

## 5. 任务产物目录约定

### 项目级规格

当前仓库存在两层规格目录：

- `../specs/`：Git 根目录下的主规格目录，上周关卡功能主要在这里。
- `specs/`：BrainPunk 子目录内的规格目录，当前 ShopPanel/UIGenerator 相关功能在这里。

新任务应优先确认 `.specify/feature.json` 指向哪一层，再写入对应规格目录，避免规格分散。

### 关卡局部文档

关卡脚本目录内保留该关卡专属知识：

```text
Assets/Game/Scripts/Level/LevelItem/Level_XX/
|-- LevelXXCtrl.cs
|-- LevelXX功能说明.md
`-- LevelXX风险评估.md
```

### 全局复用记录

跨功能可复用事实写入：

```text
DevelopMD/已有功能设计与使用记录/YYYY-MM-DD.md
```

日期采用本地日期（Asia/Shanghai）；当天文件已存在时只更新对应主题章节，保留其它任务内容，不按任务、时间戳或序号另建同日副本。
原 `DevelopMD/已有功能设计与使用记录.md` 保留为只读历史记录，不追加、改写、迁移或重新格式化。
检索既有功能时同时查阅历史文件和日期目录；模块与关卡专属文档仍按原职责维护。详见 `DevelopMD/已有功能设计与使用记录/README.md`。

只写本地证据支撑的事实；需要 PlayMode、真机或策划确认的内容写入待验证。

## 7. 工作中的禁止项

- 禁止未读规则和邻近文档就改代码。
- 禁止把假设写成事实。
- 禁止为了通用化修改已验收关卡行为。
- 禁止在未说明的情况下改存档、配置、打点、资源加载、SDK、热更、ProjectSettings。
- 禁止忽略 Prefab/Inspector 引用风险。
- 禁止只有代码实现，没有验证清单和未验证风险。
- 禁止用户验收前默认 commit/push。

## 8. 推荐执行口令

后续可以用以下口令触发对应模式：

- “按 BrainPunk 开发操作模式做”：走完整规格、实现、验证、文档同步流程。
- “先定界”：只输出目标、范围、不做范围、验收标准和风险。
- “出 Unity 操作清单”：只整理 Prefab/Inspector/资源绑定步骤。
- “做 Git 变更风险评估”：按最近三天 commit 和当前 diff 生成风险报告。
- “补文档”：只同步功能说明、风险评估和 `DevelopMD/已有功能设计与使用记录/YYYY-MM-DD.md` 当天记录；不修改原历史文件。

## 10. 遇到的问题
1. 时间过长的情况，小需求也会花很长的时间。有没有加快的方式？
2. 预期与实现不符，但是实际功能是对的，表现错误，只能去人工校验以及修正。

## 11. 标准流程需要考虑什么问题
1. 如何确定什么时候该使用 speckit 。因为流程是比较花时间的。什么时候用 planmode 或者简单调节。
2. 需要留存什么，团队协作需要什么？留存文档标准是什么，不再是策划的文档，而是程序可读的实现文档。
3. 小loop标准流程是什么？从需求开始，进行中，结束验收。
4. 大loop 标准流程是什么？什么时候优化内存记忆，什么时候强化结构？优化宪法？
5. 可以放弃一些原本的编码标准，复用性之类的问题，对项目的全局掌控性更加的重要。你需要每个模块有什么功能，什么时候可以使用这和部分。
6. 架构如何快速移植到新项目

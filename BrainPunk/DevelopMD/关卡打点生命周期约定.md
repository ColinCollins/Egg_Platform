## 2026-10-12 当前有效扩展：Dig 纳入四玩法累计

- 用户在风险及冲突告知后明确确认，将 Dig 加入 Main + Draw + IWanner 的全局累计。本节在实施前更新，并替代下文 §3.1～§3.3 中所有“三玩法累计”公式；其它时序和生命周期约束继续有效。下文三玩法描述保留为扩展前基线，不得据此排除 Dig。
- 四玩法累计成功次数 = `GameData.LevelSuccessCount` + `DrawGame.LevelSuccessCount` + `IWannerGame.LevelSuccessCount` + `DigGame.LevelSuccessCount` 的各值总和。`b_play` 采用该值；任意一种玩法成功后刷新。
- 四种玩法 `level_start.level`、失败/退出的 `level_end.level` 为上述和 + 1；成功结束前先增加当前玩法本次成功计数，成功 `level_end.level` 采用更新后的和。`level_end_success_N` 使用同一四玩法和且 N≤50；参数 level 继续使用各玩法实际配置 ID，Dig 使用 DigLevelData.Id，不使用排序序号替代。
- Dig item_category=`dig`，level_name 为进入时接受的实际 DigLevelData.Path；排序云控更新不改写活动尝试的内容身份。play_count/成功/历史 revive 按 DigLevelData.Id 存入独立 DigGame 字典，历史 total_duration 以实际 Path 存储毫秒。
- Dig 与 Draw 对齐：进入新关清时长/revive和会话资格；Reset/失败先增加 revive/历史重试、发送 fail，再清本次时长、保留同关累计 revive 和已购提示/奖励墨水资格，增加 play_count 后发新 start；成功先增加成功次数、发 success 与派生事件、再清本次时长/revive后开放胜利 UI；Replay 不增加 revive，清时长/revive后增加 play_count并发新 start，保留同关资格；退出活动尝试发 exit 后清现场及会话资格。
- DigLevel_999 具有原表中的实际配置 ID 40999，沿用开始/手动 Reset/退出统计，但关卡不可成功，不写普通 PassedLevels/星级/奖励。传送门请求主线被接受后可上报既有 enter_tbc_portal(type=Dig=3)，失败不报；不能伪造成功或解锁普通关。

## 2. 当前生命周期契约

### 2.1 进入新关

- 更新为新关的 ID 与资源路径，清理上一关的时长、revive、提示显示状态和提示获取资格。
- 当前关卡的持久化 `LevelPlayCount` 加一，然后发送 `level_start`；IWanner 使用小关资源 Path 作为统计键。
- Draw 或 IWanner 若切换前仍有活动打点周期，先为旧关发送 `level_end(exit)`，再建立新关上下文。

### 2.2 Reset 或失败重试

- 先记录一次 revive：主线增加 `ResetCount` 或 `FailCount`，Draw 增加
  `_analyticsReviveCount`，IWanner 增加当前小关运行态 revive；三者继续写入各自历史 `LevelReviveCount`。
- 发送与当前 `level_start` 配对的 `level_end(result=fail)`。
- 结束事件发送后清理本次时长与尝试级提示显示/提醒状态，保留当前关卡累计 revive；主线与 Draw 当前关已经通过
  金币、广告或首次免费流程获得的提示资格属于关卡会话状态，同关 Reset 或失败重试不得清除。
  - 主线使用 `ResetDataPreservingRevive()`，不得改变共享 `ResetData()` 的原全量清理语义。
  - Draw 清零 `_analyticsCurrentLevelTimeSeconds`，保留 `_analyticsReviveCount` 与当前关提示获取资格；
    新 DLevel 实例的提示显示状态由该资格重新派生，避免玩家重复付费或看广告。
  - IWanner 清零当前尝试时长，保留当前小关累计 revive。
- 当前关卡 `LevelPlayCount` 加一，再发送新的 `level_start`，随后重建关卡。
- 连续 Reset 的失败结束事件 revive 依次为 `1、2、3...`；最终成功结束事件仍携带累计值。

### 2.3 成功结算

- 先写入当前玩法成功次数，再发送 `level_end(result=success)`。
- `level_end` 以及它同步触发的相关打点完成后，清理当前时长、revive 和尝试级提示显示状态；
  Draw 当前关提示获取资格继续保留到切换关卡、返回选关页或退出 Draw，VictoryPanel 可交互时打点状态已经干净。
- 三种玩法成功都在 `level_end(result=success)` 后发送 `level_end_success_N`。
- `N` 使用主线、DrawGame 与 IWannerGame 写入本次成功后的累计成功次数之和；事件参数 `level`
  使用当前玩法实际关卡 ID。IWanner 正常通关与激励 Skip 成功均视为小关成功；Group 完成不重复累计。
  派生事件完成后再进入成功运行态清理。

### 2.4 VictoryPanel Replay

- 业务语义中的 Replay 只指 VictoryPanel 的 Replay 按钮，Reset 不属于业务 Replay。
- Replay 本身不增加 revive；它清理时长、revive 和尝试级提示显示状态，`LevelPlayCount` 加一后发送
  新的 `level_start`，再重建当前关卡。主线 VictoryPanel Replay 开启新的答案会话并清除提示资格；Draw Replay
  仍属同一关卡会话，重建时从已保留的提示获取资格恢复提示显示，不重复收费；切换关卡、返回选关页或退出 Draw
  才清除该资格。

### 2.5 退出

- 活动关卡周期在退出或切换玩法前发送 `level_end(result=exit)`；随后由对应控制器清理现场。主线进入
  `ChoiceLevelPanel`、Draw 返回选关页或退出玩法时同时清除当前关提示获取资格和提示显示状态，防止下一次关卡会话继承。

## 3. 字段口径

### 3.1 level_start

- 公共字段：`level`、`level_name`、`item_category`、`play_count`、`start_type`。
- `item_category`：主线为 `main`，Draw 为 `draw`，IWanner 为 `iwanner`。
- `play_count`：只读取当前玩法、当前关卡的 `LevelPlayCount`；历史 `LevelReviveCount` 不参与计算。
- `start_type` 与按钮来源解耦，所有开始事件统一按“当前关卡是否已经通关”判断：
  - 当前关卡存在于对应 `PassedLevels`：`replay`。
  - 当前关卡尚未通关：`play`。
- 三种玩法的 `level_start.level` 均使用主线、DrawGame 与 IWannerGame 历史累计成功次数之和加一，
  保证玩家在三种玩法之间切换时使用同一套连续进度序号。
- IWanner 的 `start_type` 使用当前小关 Path 对应的历史 `LevelSuccessCount` 判断；成功次数大于 0 为
  `replay`，否则为 `play`。Group 通关状态不替代小关是否通关的判断。

### 3.2 level_end

- 公共字段：`level`、`level_name`、`item_category`、`duration`、`level_duration`、
  `revive`、`total_duration`、`result`。
- `result` 映射：成功为 `success`，Reset/失败为 `fail`，退出为 `exit`。
- 三种玩法的 `level_end.level` 均使用跨玩法累计口径：成功使用主线、DrawGame 与 IWannerGame 写入
  本次成功后的累计成功次数之和，失败/退出使用跨玩法累计成功次数之和加一；同一尝试的开始与结束
  保持同一进度序号。
- `revive` 读取当前关卡运行态累计值，不读取历史 `LevelReviveCount`：
  - 主线：`ResetCount + FailCount`。
  - Draw：`_analyticsReviveCount`。
  - IWanner：当前小关运行态累计 revive；自动失败与手动 Reset 各增加一次，失败后的 Reset 点击不重复增加。
- 每次 Reset 的结束事件发送后都会重新开始计时；revive 不清零，直到成功结算或
  VictoryPanel Replay 开启新周期。
- 三种玩法的 `total_duration` 均读取各玩法持久化 `LevelPlayDuration`：每次发送
  `level_end` 前，先把本次 `duration` 累加到当前关卡的历史值并保存，再把更新后的历史累计值
  作为 `total_duration` 上报。Draw、IWanner 与主线一致，以关卡资源路径作为累计字典键，单位均为毫秒。
- Draw 旧版本未写入历史时长，无法追溯补齐；升级后从现有存档值开始继续累计。

### 3.3 跨玩法累计与派生事件

- `b_play` 使用主线、DrawGame 与 IWannerGame 的历史累计成功次数之和；任一玩法成功结束后立即刷新。
- 三种玩法成功都发送 `level_end_success_N`，其中 `N` 使用三玩法累计成功次数之和；主线事件参数
  `level` 使用当前实际主线关卡 ID，Draw 使用当前 `DrawLevelData.Id`，IWanner 使用当前
  `IWannerLevelData.Id`。`N > 50` 时三种玩法都不上报。

### 3.4 虚拟货币事件关卡上下文

- `earn_virtual_currency.level_name` 与 `spend_virtual_currency.level_name` 统一使用当前会话最近一次
  `level_start.level_name`，三种玩法的开始事件都会刷新该值。
- 退出关卡或返回选关界面不会清理最近关卡名；因此从 Draw 或 IWanner 关卡退出后购买金币或消费金币，仍使用
  最近一次关卡的 Path，直到下一次主线、Draw 或 IWanner `level_start` 覆盖。
- 应用启动后若本会话尚未发送任何 `level_start`，继续回退到主线当前关卡路径；主线关卡数据缺失时
  使用既有 `no_start` 降级值。本次上下文只保存在运行时，不新增存档字段。

### 3.5 IWanner TBN 边界

- TBN `ILevel_999` 复用小关的开始、失败、Reset 与退出事件口径，但不写入普通 Group 进度。
- TBN 若没有有效 `IWannerLevelData.Id`，成功派生事件 `level_end_success_N` 必须安全跳过并记录告警；
  不得使用 GroupId 或伪造 ID。当前产品要求 TBN 不可通关，因此正常流程不会产生成功结束事件。

## 4. 标准事件序列示例

未通关关卡连续 Reset 两次后成功：

```text
level_start(start_type=play, play_count=1)
level_end(result=fail, revive=1)
level_start(start_type=play, play_count=2)
level_end(result=fail, revive=2)
level_start(start_type=play, play_count=3)
level_end(result=success, revive=2)
level_end_success_N(level=当前玩法实际关卡ID)
清理时长、revive、尝试级提示显示状态（Draw 当前关提示获取资格保留到离关）
VictoryPanel Replay
level_start(start_type=replay, play_count=4)
```

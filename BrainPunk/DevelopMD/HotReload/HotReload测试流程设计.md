# HotReload 测试流程设计 — 功能设计文档

创建时间：2026-05-21  
版本：v1.0  
适用范围：BrainPunk 当前 `LoadManager -> HotReloadCtrl -> YooAsset` 启动热更链路。

## 概述

本文设计一套适合当前项目的热更测试流程，目标是把“生产构建”和“正式上线”拆成两个独立环节，让你可以先用接近正式环境的产物做完整验证，再决定是否对真实线上用户生效。

核心原则只有一句：

- 构建出的 App 和资源包先变成不可变的候选产物。
- 测试验证只针对候选产物进行。
- 正式上线只做“发布动作”或“路由切换”，不重新打包、不重新生成资源。

## 目标与背景

### 目标

1. 让测试包尽量接近正式生产包，避免“测试能过，正式不能过”。
2. 让热更测试环境和真实线上用户环境隔离，避免误伤线上。
3. 让上线动作变成可回滚、可重复、可审计的独立步骤。
4. 让单次测试能覆盖“基础包 + 热更包 + RemoteConfig + CDN + 缓存”整条链路。

### 背景

基于当前代码，HotReload 有几个已知特征：

- 默认入口是 `LoadManager.HotReload()`，启动时同步阻塞等待热更完成。
- 配置表 `ConfigManager` 依赖当前资源包内的 `Assets/Game/Configs/*.json`。
- 热更失败或超时后，主流程仍可能继续进入后续流程。
- CDN 地址来自 `GameSettingData.Setting.GetCdnUrl()`。
- 当前 `HotReloadCtrl` 的 Host 模式没有真正使用 `BuiltinPackageElement.generation`，而是把 `generation` 固定成 `"0"`。

这意味着测试流程如果不把环境、缓存、版本号分开，很容易出现：

- 测试 CDN 污染正式环境。
- 旧缓存影响测试结果。
- 同一安装包在不同环境之间切换后结果不可重复。
- 测试通过的资源不是最终上线的那一份。

## 功能需求

### 核心流程

设计采用四条 lane：

1. 本地模拟 lane
2. 测试热更 lane
3. 预发布演练 lane
4. 正式线上 lane

其中：

- 本地模拟 lane 用于开发自测，不参与上线判断。
- 测试热更 lane 用于 QA / 开发联调，环境与线上隔离。
- 预发布演练 lane 使用“正式候选产物”，但不对真实用户开放。
- 正式线上 lane 只接收已经在预发布演练 lane 通过验证的同一批产物。

### 功能清单

需要隔离的维度至少有五个：

| 维度 | 测试环境 | 正式环境 | 是否必须隔离 |
|---|---|---|---|
| App 构建标识 | `qa` / `rc` | `prod` | 建议 |
| CDN / 资源根路径 | `staging` | `prod` | 必须 |
| 资源版本命名 | `rc-*` | `prod-*` | 必须 |
| RemoteConfig 来源 | `staging` | `prod` | 强烈建议 |
| 本地缓存 / 安装态 | 独立 | 独立 | 必须 |

### 边界与约束

当前项目要注意三个现实约束：

1. `HotReloadCtrl` 当前没有把 `generation` 接通到正式流程。
2. `Assets/Resources/GameSetting.asset` 当前默认 `playMode = EditorSimulateMode`，正式测试前必须确认构建流程会改成 `HostPlayMode`。
3. `GameSetting.SetCdnUrl(string cdn)` 当前写本地存储的顺序有问题，不适合直接当测试切环境入口。

因此这份流程设计分为：

- 立即可执行版：不依赖代码改造，也能跑。
- 推荐完整版：补少量环境切换能力后，测试效率更高。

## 接口设计

### 环境模型

建议统一定义 4 个环境名：

| 环境名 | 用途 | 资源来源 | 线上可见性 |
|---|---|---|---|
| `local-sim` | 编辑器自测 | 本地模拟 manifest | 不可见 |
| `staging-hotfix` | 热更联调测试 | 测试 CDN | 不可见 |
| `release-rehearsal` | 正式候选演练 | 预发布 CDN / 正式镜像 CDN | 不可见 |
| `prod-online` | 正式线上 | 正式 CDN | 可见 |

### 产物模型

把热更相关产物拆成三类：

| 产物 | 说明 | 是否允许上线时重新生成 |
|---|---|---|
| App 安装包 | APK / IPA / AAB / EXE | 不允许 |
| 资源包产物 | Bundles / `.version` / manifest | 不允许 |
| 发布路由 | CDN 指向、别名、当前版本映射 | 允许 |

关键约束：

- 测试验证通过后，上线只能切“发布路由”。
- 不允许重新出一版“长得一样”的资源再上线。

### 事件 / 回调关注点

测试记录必须覆盖这些节点：

- `INITIALIZE_PACKAGE`
- `REQUEST_PACKAGE_VERSION`
- `UPDATE_PACKAGE_MANIFEST`
- `CREATE_DOWNLOADER`
- `DOWNLOAD_PACKAGE_FILES`
- `CLEAR_CACHE_BUNDLE`
- `START_GAME`

同时记录：

- 当前 `playMode`
- 当前 CDN 地址
- 当前包名
- 当前 package version
- RemoteConfig 是否拉取成功
- 是否命中缓存

## 实现方案

### 架构位置

流程设计建议把职责拆成三层：

1. 构建层
2. 发布层
3. 测试验证层

其中：

- 构建层只负责生成候选产物。
- 发布层只负责把候选产物挂到某个环境入口。
- 测试验证层只负责安装、切环境、跑用例、记录证据。

### 关键逻辑

#### A. 环境分层策略

推荐使用“两套资源环境 + 一套正式候选镜像”的结构：

| 层级 | 路径示例 | 用途 |
|---|---|---|
| 测试 CDN | `.../hotfix/staging/<buildId>/` | QA / 开发热更验证 |
| 预发布镜像 | `.../hotfix/rehearsal/<buildId>/` | 正式候选演练 |
| 正式 CDN | `.../hotfix/prod/current/` | 真实线上 |

建议规则：

- `staging` 可以反复覆盖。
- `rehearsal` 一次构建一个目录，不覆盖。
- `prod/current` 只能由“通过验证的 rehearsal 目录”提升而来。

#### B. 生产构建与上线动作分离

推荐把整个流程切成五段：

1. 生成候选产物
2. 上传到测试环境
3. 通过测试环境验证
4. 复制同一份产物到预发布演练环境
5. 通过后把同一份产物提升到正式线上

具体要求：

- 阶段 1 只出包，不上线。
- 阶段 2 只发到测试环境，不碰正式环境。
- 阶段 3 跑完整热更验证矩阵。
- 阶段 4 不重新打包，只换部署位置。
- 阶段 5 只做“指向切换”或“目录提升”。

#### C. 推荐的环境切换方式

优先级从高到低建议如下：

1. 构建时注入环境配置
2. 本地调试开关覆盖 CDN / RemoteConfig 环境
3. 读取独立的环境配置文件
4. 修改 `GameSetting.asset`

不建议把“手改 `GameSetting.asset` 再提交”作为日常测试手段，因为：

- 容易把测试配置带进正式提交。
- 容易污染其他人的工作区。
- 无法稳定复现。

#### D. 当前项目的最小可执行流程

在不改代码的前提下，最保守的流程如下：

1. 用正式构建参数生成一份候选 App 和资源包。
2. 把资源包先上传到 `staging` 目录。
3. 准备一个测试专用安装包，内部 `GameSetting` 指向测试 CDN，并确保 `playMode = HostPlayMode`。
4. 测试安装包只连接 `staging`，跑热更验证。
5. 验证通过后，不重打包，把同一份资源复制到 `rehearsal`。
6. 用正式候选包再跑一轮接近上线的演练。
7. 演练通过后，把 `rehearsal` 的同一份资源提升到 `prod/current`。

这个版本的缺点是：

- 需要至少两种安装包或两套构建配置。
- 环境切换偏人工。

但它今天就能执行。

#### E. 推荐完整版流程

如果后续补 2 个小能力，流程会顺很多：

1. 增加运行时环境选择入口
2. 增加环境态可视化

建议补的能力：

- GM / Debug 面板里显示当前 `CDN`、`playMode`、`packageVersion`、RemoteConfig key。
- 支持测试包在运行时切到 `staging-hotfix` 或 `release-rehearsal`。
- 本地缓存按 `env + packageName + version` 分桶。

这样以后你只需要一份测试安装包，就可以切换环境并重复验证。

### 标准测试流程

#### 流程 1：日常热更联调

1. 开发生成候选资源包，标记 `buildId`。
2. 上传到 `staging/<buildId>/`。
3. 安装测试包，确认当前环境是 `staging-hotfix`。
4. 清理缓存或使用全新安装。
5. 启动游戏，观察热更节点完整走通。
6. 验证配置表、主场景、关卡资源、字体和 UI。
7. 记录日志、截图和资源版本。

#### 流程 2：正式上线前演练

1. 从已通过 `staging` 的候选产物中选定一份 `buildId`。
2. 原样复制到 `rehearsal/<buildId>/`。
3. 使用正式候选安装包连接 `release-rehearsal`。
4. 跑全量回归：新装、覆盖安装、旧缓存升级、弱网、断网重启。
5. 若通过，则锁定该 `buildId`，禁止再次重打。

#### 流程 3：正式上线

1. 只允许提升已经通过 rehearsal 的 `buildId`。
2. 把 `rehearsal/<buildId>/` 提升到 `prod/current/`，或切换正式别名到该目录。
3. 正式上线后只做线上验证，不做重新构建。
4. 如有问题，回滚正式别名到上一版目录。

### 推荐验证矩阵

每次至少验证以下场景：

| 场景 | 目的 |
|---|---|
| 新装首次启动 | 验证完整冷启动热更 |
| 已安装旧版本覆盖 | 验证升级链路 |
| 已有旧缓存再启动 | 验证缓存兼容 |
| 热更中断网 | 验证失败与重试 |
| 热更完成后二次启动 | 验证缓存复用 |
| RemoteConfig 为空 / 超时 | 验证降级路径 |
| 资源已更新但不需下载 | 验证 manifest / version 判定 |

### 回滚方案

严格区分两种回滚：

1. 测试回滚
2. 线上回滚

测试回滚：

- 删除 `staging` 当前候选目录。
- 测试包清缓存后重新连旧目录。

线上回滚：

- 只允许回滚发布路由。
- 不允许线上紧急回滚时重新打补丁替换。

推荐做法：

- 保留至少最近 2 个正式可用目录。
- `prod/current` 始终是一个可切换指针，不是唯一资源存储位置。

### 变更清单

如果要把这套流程彻底做顺，建议后续最少补这些改动：

1. 让 `HotReloadCtrl` 真正接入 `generation`。
2. 增加测试环境选择入口，不依赖手改 `GameSetting.asset`。
3. 修正 `GameSetting.SetCdnUrl()` 的本地存储写入顺序。
4. 在 Loading 或 GM 面板显示当前热更环境信息。
5. 把缓存目录或缓存 key 按环境隔离。
6. 把 RemoteConfig 环境也独立出来。

## 验收标准

满足以下条件，说明流程设计可用：

1. 同一份候选资源可以先在测试环境验证，再在正式环境上线，不重新打包。
2. 测试环境的资源、RemoteConfig、缓存不会污染正式线上。
3. 线上上线动作可以独立回滚到上一版候选资源。
4. 测试记录能明确回答“当前测的是哪份资源、哪个环境、哪个版本”。
5. 出现问题时可以区分是构建问题、资源问题、配置问题，还是上线路由问题。

## 操作清单 — HotReload 测试执行

### 1. 准备候选产物

- 生成一份带唯一 `buildId` 的候选资源包
- 记录 App 版本、资源版本、构建时间、提交号

### 2. 部署到测试环境

- 上传到测试 CDN 路径
- 确认测试包只指向测试环境
- 不要覆盖正式线上目录

### 3. 清理状态

- 卸载旧测试包或清空本地缓存
- 确认不是用上一次缓存结果在“假通过”

### 4. 执行验证

- 启动游戏，记录热更日志
- 记录是否下载、下载量、是否超时、是否失败
- 验证主场景、配置表、关键关卡和字体资源

### 5. 演练上线

- 把同一份候选资源复制到 rehearsal
- 用正式候选包再跑一遍验证

### 6. 正式上线

- 只提升 rehearsal 已通过的目录
- 上线后做冒烟验证

### 7. 回滚预案

- 准备上一个正式可用目录
- 出现问题时只切路由，不重打包

# 2026-10-16 P0 哨兵与低编号关卡复核

## 结论

- 本轮整体风险等级为 **P0**。其中 P0-1、P0-2 有项目内用户实测记录与当前源码共同支撑；P0-3 是代码可达的条件风险，但尚无真机卡死日志；P0-4 是用户明确要求的低编号关卡强制发布门禁，并非已证实故障。
- 三天窗口内未直接改动 `ClassCollector`、`link.xml`、`LoadManager` 或 RemoteConfig；直接触及的 P0 哨兵为 `GameManager`、`DigPlayCtrl`、`DigLevelCtrl`、`DrawPlayCtrl`、`IWannerPlayCtrl`、OneLink SDK 接入和广告依赖配置。

## P0-1：Germ 正式关卡掉出地图的实测问题仍未闭环

- **问题**：`DigGame功能说明.md:232` 保留用户正式关卡实测：Germ 掉出地图，调试列表仍有三只病菌；原因、发生位置和 Sand 碰撞链尚未查证。该状态可能使需要吞噬全部 Germ 的关卡无法继续。
- **影响文件**：`Assets/Game/Scripts/Level/DigLevel/DigGermCtrl.cs`、`DigActorCtrl.cs`、`DigLevelCtrl.cs`、`DigTerrainCtrl.Editor.cs`，以及 `DigGerm_001`～`DigGerm_006` 和低编号 DigLevel Prefab。
- **Git 依据**：`60ecdc8db feat(dig): 支持 Germ 实体碰撞及编辑器播放态地图按钮` 在本三天窗口内修改上述脚本并将一个 Germ prefab 拆为六个；`e9f13b91f DigLevel 1-5 关设计` 又重写低编号关卡资源。
- **扩散链路**：Germ prefab 的 Collider/Rigidbody → `DigGermCtrl.Initialize/SetPaused` → Unity Physics2D 与 Sand/地图碰撞 → `DigActorCtrl` 接触上报 → `DigLevelCtrl` 的待吞噬集合与成功条件 → 关卡可完成性。
- **建议**：发布前在当前 001～006 正式 Prefab 上复现并录制掉落前后 Rigidbody/Collider、Sand 碰撞层和世界坐标；以“所有列表内 Germ 均保持可达并能被吞噬/失败能收束”为验收。原因未定位前不可用隔离地面支撑用例宣称闭环。

## P0-2：无上跳失败改成固定 Ease 下坠，速度连续性与用户实测不一致

- **问题**：`DigFailAreaHandle.cs:19,43` 以 `playDeathHop=false` 进入统一失败；`DigLevelCtrl.cs:447-466` 先冻结状态再调用死亡表现；`DigActorCtrl.cs:85-103` 虽保存物理速度，但 `PlayDeath` 在 `116-134` 关闭物理并用固定 `DOMoveY(...).SetEase(Ease.InQuad)` 下坠，没有使用保存速度。`DigGame失败条件功能与风险记录.md` 已记录用户实测“去掉上跳后下落速度仍变化”。
- **影响文件**：`DigFailAreaHandle.cs`、`DigTrapFailureHandle.cs`、`DigActorCtrl.cs`、`DigLevelCtrl.cs` 和挂载失败区/陷阱的低编号关卡 Prefab。
- **Git 依据**：`e9f13b91f` 新增 `DigFailAreaHandle.cs` 并修改 Actor、LevelCtrl、陷阱失败组件；本轮资源把该链路带入 001～007/012。
- **扩散链路**：FailArea/Trap 碰撞 → `TryFail` → `BeginFailure`/结果锁 → Actor 物理冻结 → DOTween 固定时长下坠 → `Resolved(Failed)` → 重建。速度突变是玩家可观察表现，不是仅内部数值差异。
- **建议**：先明确产品验收是“保留碰撞瞬间垂直速度”还是“统一固定死亡速度”，再在同一关对比普通坠落、FailArea、Trap 三入口的首帧/末帧速度曲线；当前不可宣称已解决。

## P0-3：Dig 胜负收束依赖插屏结果回调，缺失回调时没有本地超时

- **问题**：`DigPlayCtrl.cs:344-345` 只有插屏回调后才创建胜利面板；失败重建在 `458-464` 用 `UniTaskCompletionSource` 等回调后才揭黑幕和恢复输入。`InterstitialAdHelper.cs:96-107` 已有一次性回调防重，早退也会失败回调，这是已缓解项；但 `GameSDKService.Ads.cs:54-57` 在 `_adsManager` 为空时不会回调，`GameAdsManager.cs:140` 也只等待底层 SDK Task，没有调用方超时/取消兜底。
- **影响文件**：`DigPlayCtrl.cs`、`InterstitialAdHelper.cs`、`GameSDKService.Ads.cs`、`GameAdsManager.cs`、当前未提交的 FusionAds 1.5.2 Android 解析配置。
- **Git 依据**：三天窗口内多次修改 `DigPlayCtrl` 和失败入口；当前工作区把 `fusionads` 由 1.5.1 切到 1.5.2，使底层完成语义仍需重新验证。
- **扩散链路**：关卡成功/失败 → 结果锁与输入关闭 → 广告策略 → FusionAds/原生覆盖层 → 结果回调 → 胜利面板或黑幕揭开；若底层既不成功也不失败，玩家停留在锁定/遮黑状态。
- **建议**：在 Android/iOS 真机对“无广告库存、断网、服务不可达、打开后关闭、应用切后台、SDK 不回调”逐项验证；若 SDK 无法保证有限时间完成，应在游戏侧等待点增加可取消超时并以失败结果收束。当前仅为条件风险，尚无本轮真机挂死日志。
